## 0. 一句话结论

**不要做「日志分析工具」，要做「AI 取日志时的取证层」。**

你现在被拿来和阿里云 SLS / Datadog 比，那是错的赛道 —— 那是监控平台，
要 Agent 埋点、要数据上云、按 GB 计费，你一个本地小工具永远打不过，
也不该去打。

真正的赛道是 2026 年新开的：**AI 编码 Agent 需要读日志，但没人给它一个像样的取证工具。**
Agent 现在只会 `grep` + `tail` + 硬塞进上下文。这块地是空的。

你的核心壁垒一句话：

> **我们不把日志交给 LLM。我们用确定性算法把日志变成可引用的证据，LLM 只读证据。**

这句话不是营销，是可验证的技术立场。后面第 3 节给出为什么它成立。

## 2. 白地在哪里：四个没人做的洞

### 洞 1：没人把「日志压缩」做成可验证的产品

**现状**：每个人都在说自己压缩了多少，但没有一个拿出第三方可复现的证明。

- **LogDx-CI** 基准（2026）已经存在：35 个真实 GitHub Actions 失败案例，
  11 种缩减工具横向评测，3 类 LLM debugger 家族打分。它的核心结论是
  **混合 grep+tail 路由在成本-质量帕累托前沿上占优**，质量与纯 grep 持平
  但 token 少 4.5 倍。
- **Loghub 2.0**（ISSTA'24）提供 14 个真实系统数据集，**带人工标注的 ground truth**，
  平均每个 360 万行。

**这两个东西合起来 = 一个现成的、没人做的评测舞台。** 你有引擎，有压缩率
（实测 12289 倍），有人可以把它接进 Loghub 2.0 和 LogDx-CI 打榜。

> **这是你最独特、最难被抄、也最容易出圈的东西。**
> 你已经能打印 token 经济学（"这次分析压缩后 0.06 分，不压缩 1.9 元"）——
> 整个品类里只有你在报这个数。

### 洞 2：没人把「Agent 读日志」当成一等公民

2026 年 MCP 成了行业主旋律（见第 5 节），但**所有 MCP 日志 server 都是给人用的 grep 包装**。

没有人做的是：

- 一个 MCP tool，输入日志路径，输出**已经预排好序、已经按 token 预算裁剪、
  每条结论带行号引用**的证据包
- 让 Agent 不需要自己 `grep` + 读 500 行，就能直接拿到排好序的根因假设

> 你已经有 7 个工具了，但工具描述还是"分析日志文件"。
> 应该改成 Agent 的**使用剧本**（见第 6 节的 `instructions` 改写）。

### 洞 3：合规叙事完全没人占，而且有一个现成的、真实的英雄故事

**2026 年 7 月 Hugging Face 遭攻击事件**（Orange Cyberdefense 整理）：

> 攻击者生成了 17000+ 条事件记录。HF 最初尝试调用商业 LLM API 做取证分析，
> **但请求被安全策略拦截了** —— 商业模型的安全护栏无法可靠判断提交者
> 是攻击者还是应急响应人员。最终 HF 只能在自己基础设施上部署开源
> GLM-5.2 完成分析。
>
> 附带好处：日志中的凭据**从未离开 HF 环境**。

**这是你这个产品最强的单页文案。** 世界上最先进的 AI 公司，
在真实事故里用不了商业 LLM API，因为安全策略挡住了攻击日志。

你的产品答案就是：**根本不需要 LLM 来做第一步。确定性算法在本地把日志
变成证据，涉密内容不出网，LLM 只看压缩后的结论。**

### 洞 4：确定性 vs 概率性的立场没人明确表过态

NetForensicAI 和 AgentTrace 都在 DFIR 领域把这条讲透了，但在**研发/运维日志**
领域几乎没人说。而这恰恰是日志分析最大的风险点：

- LLM 会编造一个不存在的根因 —— 在凌晨三点这是致命的
- LLM 的输出不可复现 —— 同一个日志两次分析结论不同，无法写进事后复盘
- LLM 不知道"这条结论是从第几行看出来的"

> **你的 `priority_detail`（"级别35+频次25+根因20"）、`root_cause_reason`、
> `first_line`/`last_line` 已经是这个立场的雏形了，但没有被产品化表达出来。**

## 3. 核心差异化：确定性取证层

### 3.0 先把「准确率能不能超过阿里云 95%」这笔账算清楚

**结论：直接比是错的,而且你结构上做不到那 95% 覆盖的案例。但这不是坏消息
—— 它把真正的差异化指出来了。**

#### 那个 95% 到底在量什么

阿里云 SLS 原文的语境是：**「利用服务中的 Trace 数据自动生成拓扑图**，
围绕高延时分析、高错误率分析、系统热点和瓶颈进行诊断」，
在**游戏服务**这个特定场景的生产环境中准确率 95%。

它的输入是：Trace 调用链 + 自动生成的拓扑图 + 指标 + 历史数据。
**这不是「读一个日志文件」，这是「读一个已经建好拓扑的分布式系统」。**

#### 三条硬证据说明为什么不可比

**① 62.5% 的根因案例需要 ≥2 种模态。**
RCA100 数据集（部署在阿里云 ACK 的 OpenTelemetry Demo Store，
被 2025 天池 AI-Native 编程赛 5,532 支队伍使用）的分析结论：

> AIOps2025 数据集分析显示，**62.5% 的案例需要分析至少两种模态，
> 31% 需要全部三种（指标、日志、链路）才能准确诊断。**
> 仅依赖单一模态的基准会让 Agent 走不切实际的捷径。

**你的工具只有日志一种模态。这 62.5% 在结构上就不是你的战场。**

**② 实验室的 95% 到生产会腰斩。** 一个国内 AIOps 实践文章的论证（三个机制）：

- **调用链断裂**：Trace 上下文经过 Kafka / Redis / 异步 Task Worker 时，
  TraceID 频繁丢失或线程上下文传递中断 → 模型拿到的是破碎的因果链
- **高基数指标风暴**：上游网关抛 5xx，下游数十个微服务同时爆 CPU 飙升、
  连接池耗尽、GC 停顿 → 图模型/概率图模型**极易把"结果"当成"原因"**
- **LLM 幻觉**：直接喂 Log + PromQL 给 LLM，它会凭空捏造调用链路

**③ 行业标准口径根本不是 accuracy。** 社区通行的四个指标是：

| 指标 | 定义 | 业界及格线 |
| --- | --- | --- |
| **Top-K 命中率** | 真根因落在推荐前 K 个候选里 | **生产要求 Top-3 ≥ 85%** |
| **MRR** | 平均倒数排名，衡量排序质量 | 华为 Log-Insight 报 0.790 |
| **MTTI** | 从拿到异常流到输出根因的耗时 | 工业级 < 5 秒 |
| **Precision / Recall** | 需先定义"什么算对" | AIOps 挑战赛冠军 0.8216 / 0.9593 |

而且 RCA Benchmark / Cloud-OpsBench 都明确指出：

> **只看 outcome 的分数（Accuracy / F1 / Top-k）无法区分
> 「靠有效证据推理得到的正确诊断」和「靠先验偏差蒙对的幸运猜测」。**
> 对 LLM 这类容易走捷径和幻觉的系统，**诊断过程本身必须作为一等评测对象**。

#### 所以你的工具应该被什么指标衡量

不是 accuracy。是这四个，而且**后面三个全行业没人报**：

| 指标 | 含义 | 谁在报 |
| --- | --- | --- |
| **Top-3 命中率 / MRR** | 该找到的排到前面 | 行业通用，可比 |
| **自信错误率**（confident-wrong rate） | 高置信给出错误答案的比例 | **几乎没人报** ← 见 3.4 |
| **证据保留率** | 压缩后还剩多少有效证据 | **没人报** |
| **确定性指纹** | 相同输入是否产出逐字节相同的结论 | **没人报** |

**不要再宣传「准确率」。** 宣传「Top-3 命中率 + 自信错误率 + 确定性」，
前者可比，后两者是你的护城河。

### 3.1 立场陈述（建议直接写进 README 第一屏）

```
log-ai-compressor 不是日志分析工具，是日志的取证层。

我们不把日志交给大模型。我们用确定性算法把日志变成可引用的证据，
大模型只读证据。

  ✗ 同样的日志，两次分析结论不同        → 我们保证确定性
  ✗ "数据库连接池耗尽" 从哪看出来的？   → 每个结论带行号
  ✗ 日志里有 token / 身份证 / 客户名    → 内置脱敏，默认开启
  ✗ 涉密日志不敢用 AI                   → 零出网，本地算完
  ✗ 几十万行塞不进上下文                → 压成几百 token 的证据包
```

### 3.2 必须补的硬机制（这是护城河的实际形态）

现在的工具是"分析工具"，要变成"取证层"还差四样东西：

| 机制 | 做什么 | 抄谁 |
| --- | --- | --- |
| **证据 ID** | 每个结论绑定 `evidence_id`（文件 + 行号 + 哈希），报告里可跳转可验证 | NetForensicAI |
| **确定性声明** | 报告里显式区分「规则判定」和「统计推断」，并写明置信度来源。禁止用"可能""也许"糊弄 | NetForensicAI |
| **相关性 ≠ 因果** | 时间共现只能标 `related`，永远不能标 `caused`。你的 `cooccurring_clusters` 现在就是共现，必须在 UI 上把语义讲死 | NetForensicAI |
| **对抗性评测集** | 6~10 个专门设计来误导工具的场景（红鲱鱼部署、证据不足以定论、冲突指标…），每个按评分表自动打分，结果进 CI | AI Incident Investigator |

### 3.3 绝对不要做的事

| 别做 | 原因 |
| --- | --- |
| **在关键路径里加 LLM** | 根因判定、异常检测、聚类必须 100% 确定性。LLM 只能做「已有证据的翻译」，不能做「证据的生成」 |
| **做成监控平台** | 你没有 Agent 埋点、没有时序库、没有告警队列。去跟 SLS 拼是送死 |
| **加 SaaS / 账号体系** | 一旦要登录要云，"零出网"这个唯一的护城河就没了 |
| **把"AI"写成营销词** | 你的 AI 是可选的翻译层，核心是确定性引擎。宣传口径要跟实现一致，否则会失去唯一可信的差异点 |
| **宣传"准确率"** | 口径不可比，且会把你拖进和云平台比数字的陷阱。改报 Top-3 / 自信错误率 / 确定性 |

### 3.4 真正的「独一无二」：诚实的弃权

**这是全场唯一一个没有人在做的功能，也是本项目最该做出来的东西。**

Onepane（做 AI 根因分析的厂商）在讲"怎么评估 AI 根因分析的准确率"时，
说了一段话，是整份调研里最重要的发现：

> **一个自信的错误根因比没有答案更糟 —— 团队会照着它行动。**
> 任何只算命中率、不算弃权率与弃权质量的评估，
> **都会偏好那个猜得最自信的系统。**
>
> 应该一起评的指标里有：
> - **弃权率与弃权质量**：系统有多少次说"我无法确定"？
>   弃权时，声称缺失的证据是不是真的缺？
>   **在一个确实无法定论的事件上正确弃权，算通过，不算失败。**
> - **自信错误率**：高置信给出原因但错了的比例。
>   **这是最重要的数字，也是权重应该最重的数字。**
>
> 什么算好：
> 在埋点齐全的事件上追平或超过人工记录，
> 在团队自己也没解释清楚的事件上弃权，
> 准确说出缺什么证据，每条结论都链到 reviewer 能点开的原始记录，
> **自信错误率接近零**。

#### 为什么只有你能做，而云平台结构上做不了

| | 云平台（SLS / Datadog / Dynatrace） | 你的工具 |
| --- | --- | --- |
| 商业压力 | 按次调查收费，要卖"我们找到了" | 没有人付钱买一个"我不知道" |
| 界面形态 | 仪表盘 / 告警卡片，空着就是事故 | 取证报告，"证据不足"是合法结论 |
| 数据条件 | 有拓扑有指标，硬猜也有 60% 命中率 | 只有日志，猜不出来就是猜不出来 |
| 竞争对手 | 互相比较"准确率" | 没人跟它比这个 |

**一个云平台说"我不知道"，在产品上读起来像故障。你的工具说"我不知道"，
在方法论上读起来像专业。**

#### 怎么做（可执行）

**第一步：给根因判定加「置信档位」**

现在的输出是二元的「是根因 / 不是根因」。改成三档：

| 档位 | 触发条件（确定性规则） | 输出措辞 |
| --- | --- | --- |
| `CONFIRMED` | Caused-by 链直连 + 强关键词 ≥3 命中 | "根因：X" |
| `LIKELY` | 时间连锁首发 或 关键词 ≥2 | "可能根因：X（依据：…）" |
| `INSUFFICIENT` | 只有时间共现，无因果链 | **不下结论，输出缺什么** |

**第二步：给 `INSUFFICIENT` 输出一张「缺什么」清单**

这是整个功能的核心。规则化地判断当前证据缺口：

```
当前证据不足以下结论。可补齐的证据（按性价比排序）：
  1. 跨服务 Trace 或 request_id 关联  → 能确认 x 分钟内的调用因果链
     缺口：本次日志仅有 db 单服务，无上游调用方
  2. 同期指标（连接池 / QPS / 延迟） → 能区分「连接池耗尽」与「数据库慢」
     缺口：日志中连接池耗尽与查询超时同时出现，二者无法区分
  3. 变更记录（发布时间 / 配置改动） → 能确认是否为变更引入
     缺口：无变更元数据
```

**第三步：把「诚实」变成可测量的数字并公开**

建对抗性评测集（学 `AI Incident Investigator`）：6~10 个**专门设计来
误导工具**的案例 —— 红鲱鱼部署、证据薄到无法定论、冲突指标、
共现但无因果。每例按评分表自动打分：

| 评分项 | 通过条件 |
| --- | --- |
| `abstain_correctly` | 该弃权时必须弃权 |
| `missing_evidence_correct` | 说缺的证据必须真的缺 |
| `no_confident_wrong` | 不得高置信给出错误根因 |
| `causal_language_ok` | 不得把 `related` 说成 `caused` |

**第四步：发布这四个数**

```
Top-3 命中率        : XX%（对比 Loghub 2.0 人工标注）
自信错误率          : X%（越低越好，行业几乎无人公开）
正确弃权率          : XX%
确定性指纹一致性    : 100%（同输入同输出，逐字节）
```

> **一个愿意公开「自信错误率」的工具，比一个只敢公布准确率的工具可信十倍。**
> 这是把「不可信」这个全行业通病变成自己的差异点。

## 4. 优先级：给下一轮大改的排序

### P0 —— 决定生死（不做就还是"同质化"）

1. **接 Loghub 2.0 打榜**。14 个带标注的真实数据集，产出公开的
   「压缩比 vs 证据保留率」表格，贴进 README。这是**唯一别人抄不走**的东西。
2. **证据 ID + 报告可追溯**。每条结论能点回日志原文行。
3. **MCP 工具描述改写成 Agent 使用剧本**。现在的描述是给人看的，
   改成"当你需要诊断 X 时调用这个，返回什么、会花多少 token"。
4. **对抗性评测集 + 评分卡进 CI**。证明你的工具不会被误导。

### P1 —— 放大优势

5. **token 经济学面板**。界面上直接显示"本次分析：原始 X tokens →
   压缩后 Y tokens（Z 倍）→ 单次成本 ¥W"。品类里只有你在报这个数。
6. **接 LogDx-CI**。在 35 个真实 CI 失败案例上和 11 个工具对比。
7. **红线：任何 LLM 调用都必须显式 opt-in**，且状态栏常驻显示"本次分析
   发送了多少内容给谁"。这是信任的来源。

### P2 —— 扩大影响面

8. 轮转日志自动发现（现在要用户手动填 `;` 分隔）。
9. 结构化日志（JSON / logfmt）原生支持 —— 调研显示这是 AI 日志分析的前置条件。
10. trace_id / request_id 跨服务关联（这是从"单文件工具"升级到"取证台"的关键）。

## 5. 分发策略：三条渠道，其中一条几乎没人知道

### 5.1 PyPI（主战场）

**命名空间已确认可用**：`log-ai-compressor` 在 PyPI 上**未被占用**
（`pypi.org/pypi/log-ai-compressor/json` 返回 404）。

发布要点：

- **别让 fastapi/uvicorn 成为硬依赖**。现在 `dependencies` 里直接躺着
  `fastapi` + `uvicorn[standard]` + `mcp`，这会让 `pip install` 拉 30+ 个包。
  建议拆成 extras，核心引擎（core/rules/export）零三方依赖：
  ```
  pip install log-ai-compressor              # 只装 PyYAML，纯引擎
  pip install log-ai-compressor[web]         # + FastAPI/uvicorn
  pip install log-ai-compressor[mcp]         # + mcp SDK
  pip install log-ai-compressor[all]
  ```
  **轻量是 PyPI 生态的硬通货**，重依赖会直接劝退。
- 加 `project.urls`（已加）、classifiers（已加）、`Development Status`
- README 第一屏必须是上面那句立场陈述 + 那张 token 经济学表

### 5.2 官方 MCP Registry（几乎无人使用，但分发杠杆最大）

2026 年 MCP 生态收敛到了一个**官方目录**：
`registry.modelcontextprotocol.io`（2025-09-08 上线 preview，Anthropic / GitHub /
Microsoft / PulseMCP 背书）。

**关键：官方 Registry 明确支持 PyPI 包作为分发方式。** 也就是说：

> 你发一次 PyPI → 提交一个 `server.json` 到官方 Registry →
> **Smithery、PulseMCP、Docker Hub、各家 MCP 客户端的目录会自动抓取。**

提交方式：

```bash
mcp-publisher login github      # 用 GitHub 账号证明 io.github.<你的账号>/ 命名空间
mcp-publisher publish           # 提交 server.json
```

**注意事项（有实测资料支撑）**：
- 顶层 description 必须 **能力优先、少于 100 字符** —— 这正是 Agent 和目录
  质量评分器读的那一行
- 每个工具要有 name + 人类可读 title + 详细 description
  （"只写个标题当描述"会被目录评低质量分）
- GitHub 命名空间格式：`io.github.<username>/<server-name>`
- 想要更像正经产品可以用 DNS TXT 验证拿 `com.<你的域名>/<name>` 命名空间

> **建议：这一条优先级要提到 P0。** 它是"别人没有的分发渠道"，
> 而且成本极低（一个 JSON 文件 + 一次 CLI）。

### 5.3 Agent Skills 生态（新兴，值得跟）

`skills.rest` 这类站点开始收录 log-forensics 这类 Agent Skill，
安装方式是 `npx skills add <github>/<skill>`。把「怎么用这个工具查日志」
写成一个 Skill，是让 Agent 主动发现你的低成本的另一条路。

## 6. MCP 层的产品化建议

现在的 `INSTRUCTIONS` 写的是功能清单。Agent 不会照功能清单用工具，
它需要的是**剧本**。建议改成：

```
当你面对以下情况时使用本工具：

  「日志太大读不完 / 塞不进上下文」      → analyze_log_file
      返回已聚类去重的错误清单 + 根因排序 + 优先级评分。
      实测 10 万行 7MB 会压到约 150 tokens，优先用它而不是 grep。

  「用户报了个错，我要找原因」            → analyze_log_file → get_cluster_detail
      先拿排序，再对 Top 簇取典型样例与降噪堆栈。
      注意：所有结论都是确定性规则判定，每个都带行号，可以直接引用给用户。

  「这个错误具体怎么修」                  → export_report(format="summary")
      直接产出可投喂给用户的精简摘要，省得你手抄。

  「修复前后有回归吗」                    → compare_log_files
      第一个文件为基准，返回新增/消失/共同。

  不要做的事：不要自己 grep 整个日志文件。10 万行会吃掉你几乎全部上下文，
  而本工具 0.4 秒就能给你排好序的结论。

  数据不出网：除非用户在 AI 设置里显式配置了服务商，否则不会有任何
  日志内容离开本机。
```

这段话本身就是差异化 —— 别的 MCP 日志 server 都在说"我能搜日志"，
你在教 Agent **别**去搜日志。
